# 02 — Backlog & Tech-Debt Ledger

**The single source of truth for everything we consciously deferred.** The
Roadmap (`01_Development_Roadmap.md`) tracks *modules and phases*; this tracks
the cross-cutting items — performance polish, security, infra, testing gaps, UX,
and product decisions — that would otherwise get lost between modules.

## Discipline (non-negotiable)
- **Every time we say "later", it gets an entry here** — same commit, ideally.
- Nothing ships to production (Internal GA, Phase 8) with an open **🚩 Go-live**
  item. That column is the launch gate.
- When an item is done, mark it `DONE` with the date (don't delete — the history
  is the record). Detailed rationale lives in the linked source doc; this is the
  index.

**Priority:** P1 critical · P2 high · P3 medium · P4 scale-later.
**🚩 Go-live** = must be resolved before real users (Phase 8).

| REC-1 | **Recurring issues** (V2 module 32) | P1 | No | ✅ DONE 2026-08-22 | ADR-0051. Per-project templates with a schedule; each firing stamps out a **new issue**. The decision that shaped everything: ClickUp offers "reset the same task" and that is **wrong for this product** — cycle time and velocity replay from status transitions (ADR-0031), so one row completed fifty-two times has no cycle time at all and its `createdAt` makes the fiftieth standup read as a year of lead time. Jira's Create-issue action is right and this matches it. | REC-2 | **The scheduler is an HTTP tick, not a queue or a platform primitive** | P2 | No | ✅ DONE 2026-08-22 | ADR-0051 §5-§6. `POST /api/scheduler/tick`, bearer-authenticated with `SCHEDULER_SECRET`, callable by Vercel Cron, a Kubernetes CronJob, a systemd timer or GitHub Actions — no bet on the current host (ADR-0004), no worker to run. Safe to retry because each due recurrence is **claimed with a conditional update on `nextRunAt`** (ADR-0011's trick), so two overlapping ticks cannot both create the issue. Proven under real concurrency rather than asserted: two simultaneous ticks against 26 due recurrences split them 13/13 with **zero overlap and zero duplicates**. Refuses every request while the secret is unset — an unauthenticated scheduler endpoint is an unauthenticated issue factory. |
| REC-3 | 🚩 **The cron job has to be configured per deployment** | P1 | **Yes** | OPEN | Nothing fires until something calls `POST /api/scheduler/tick` hourly with the `SCHEDULER_SECRET` bearer token. | REC-4 | **A dead scheduler is silent** | P2 | No | OPEN (mitigated) | The failure mode this module has and no other does: if the tick stops, recurrences produce nothing and nothing says so. | REC-6 | **Time zones are per recurrence, not per user or per org** | P3 | No | OPEN | ADR-0051 §7. | REC-7 | **No recurring subtask sets, sprints, or natural-language schedules** | P4 | No | OPEN | ADR-0051 "Not decided here". | AUT-1 | **Automations** (V2 module 31) | P1 | No | ✅ DONE 2026-08-22 | ADR-0050. Per-project **trigger → conditions → actions**, the shape Jira, ClickUp and Asana all use. Four triggers, six condition types, five actions, caps of 10/5/20. The four safety properties are the module, not the trigger list: **(1)** an automation's own write never fires another rule (BR-2) — the guard is the actor, checked before any IO, so the accidental "when status changes, change status" costs one boolean rather than a cascade; **(2)** every write is attributed to the **rule**, so an activity feed never claims a person did what a rule did (BR-3); **(3)** rules run after the primary write commits and are best-effort, so an automation can never fail or roll back the action a person took (BR-4); **(4)** every evaluation is logged including `SKIPPED`, naming the condition that stopped it — "why didn't my rule fire" is the more common question (BR-5). The engine is a pure function from `(event, rules)` to a plan (28 unit tests); the service does the IO (26 integration tests). | AUT-2 | **An automated comment needed a nullable `Comment.authorId`** | P2 | No | ✅ DONE 2026-08-22 | ADR-0050 §4 claimed a rule-id actor "needs no fake user row". | AUT-3 | **The write's response showed the value from before the rule ran** | P2 | No | ✅ DONE 2026-08-22 | Creating a bug under an "escalate new bugs" rule returned `priority: LOW` — the row was read before dispatch and the DTO built from it. ## Remaining V1 modules
Tracked in `01_Development_Roadmap.md §2`. **All V1 modules are built** as of
2026-08-08 — Phase 4 (Auth, Projects, Issues, Board, Home), Phase 5 (Backlog,
Sprint, Comments incl. mentions/threads per ADR-0038, Attachments) and Phase 6
(Notifications, Reports, Search, Admin, User Management, Roles, Profile), plus

**Phase 4–6 is therefore closed and the program is at the Phase 7 gate
(Hardening).** What remains is not modules: it is the security review (GL-2),
the load test (GL-7), an accessibility pass and cost validation, plus the
go-live blockers above. Individual feature gaps live in the per-module `FUT-*`
and `CMT-*` rows — none of them blocks the gate.

table, `Issue.sprintId`/`rank`/`version`, and the `issues(projectId, sprintId, rank)`
index (ADR-0014). Prod just needs the `sprints` table to exist (part of the manual
baseline reconciliation, GL-4/DB-2).
