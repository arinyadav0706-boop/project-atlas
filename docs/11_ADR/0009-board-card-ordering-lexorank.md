# ADR-0009: Board Card Ordering — String Fractional Ranking (LexoRank-style)

**Status:** Accepted (supersedes ADR-0007)
**Date:** 2026-07-19
**Deciders:** Founding CTO; founder direction (build for future scale, Jira-grade)

## Context

Supersedes ADR-0007, which chose float fractional indexing to avoid a schema
migration. That reasoning was mis-prioritised: EAGLES is an explicit Jira-grade
clone built for future scale, and **now — with only a handful of dummy issues —
is the cheapest possible time** to adopt the robust ordering scheme. Deferring it
would hand a painful, high-risk migration to a future with real traffic.

Float fractional indexing has a real ceiling: repeatedly inserting between the
same two neighbours exhausts float precision after ~50 operations, requiring a
column rebalance. String fractional ranking (the "LexoRank" family, used by Jira)
has **no such ceiling** — you can always generate a key between two keys — and
handles filtered reorder (ADR-0008) cleanly.

A hand-rolled key generator is deceptively hard: a naive midpoint algorithm
breaks at boundary cases (e.g. inserting before the smallest key). This is a
known-hard primitive with published, correct implementations.

## Decision

Order board/backlog cards by a **string `rank`** column holding
lexicographically-sortable fractional keys, generated by the proven,
zero-dependency **`fractional-indexing`** algorithm (`generateKeyBetween` /
`generateNKeysBetween`, base-62). Rename `Issue.boardOrder Float` → `Issue.rank
String`.

- **Create / append:** `generateKeyBetween(lastRankInColumn, null)`.
- **Reorder between two cards:** `generateKeyBetween(beforeRank, afterRank)`.
- **Move to top / bottom / empty column:** `generateKeyBetween(null, firstRank)`
  / `generateKeyBetween(lastRank, null)` / `generateKeyBetween(null, null)`.
- A move writes **one row**. No rebalance is ever required (no precision ceiling).

Adopt it **now** via a schema migration + a trivial backfill of existing issues.

## Alternatives Considered

| Option | Rejected because |
|---|---|
| **Float fractional (ADR-0007)** | Precision ceiling → needs periodic rebalance; mis-prioritised "avoid migration now" when the migration is free today. Superseded. |
| **Hand-rolled string keys** | Boundary cases (insert-before-smallest) are subtle; a naive version was shown to break. Correctness of a known-hard primitive beats avoiding a 1-file, 0-dep library. |
| Integer gaps / linked-list order | Renumbering / multi-row writes. |

## Consequences

- **Positive:** no precision ceiling, no rebalance job; one-row writes; correct
  boundaries via a proven algorithm; works under filtering; the industry-standard
  approach for a Jira-grade product; adopted at the cheapest possible moment.
- **Negative / trade-offs accepted:** a one-time schema migration
  (`boardOrder Float` → `rank String`) with a backfill of existing rows (trivial
  at current volume); one small, portable dependency (`fractional-indexing`),
  justified because it's a pure-algorithm, zero-dependency library (no vendor
  lock-in, satisfies rule #8).
- **Environment dependency — the `rank` column MUST use `COLLATE "C"` (byte
  ordering).** The base-62 keys mix upper and lower case; under a locale
  collation (e.g. `en_US.UTF-8` or an ICU collation) they mis-sort — a card
  dragged to the top gets a negative-magnitude `Z…` key that a locale collation
  sorts to the *bottom*, silently breaking board order (proven; the failure is
  invisible under a `C`/`C.UTF-8` test DB, which is how it initially slipped
  past testing). Pinning the column to `COLLATE "C"` makes ordering identical on
  every Postgres host regardless of the server default locale — this is what
  keeps the scheme portable across all hosting options (ADR-0004). This is a
  **Postgres-specific** assumption; see `docs/01_Architecture/06_Portability_Boundary.md`.
  If EAGLES ever supports a non-Postgres SQL engine (not a current goal), the
  byte-ordering requirement must be re-established for that engine.
- **Follow-up actions (implementation phase):**
  1. Migration: add `rank String`, backfill per `(project, status)` column
     ordered by `createdAt` via `generateNKeysBetween`, drop `boardOrder`,
     replace index `(projectId, status, boardOrder)` → `(projectId, status, rank)`.
  2. `createWithKey` appends a rank (not `Date.now()`).
  3. `PATCH /issues/{id}/rank` uses `generateKeyBetween` on the destination
     neighbours (RBAC + workflow validated), single-row write.
  4. Tests: unit (key ordering, boundaries) + a **fuzz test** (thousands of
     random inserts → order preserved, keys unique) + integration reorder tests.
  5. Retire the ADR-0007 rebalance item (UX-4) — not needed with string keys.
  6. Pin `rank` to `COLLATE "C"` (migration `20260720000000_rank_collation`) and
     guard it with an integration test asserting the column's collation is `C`.
